# 여행 영상 파이프라인 사용량·운영 감사

결론: 산출물은 완료했지만, 비용과 운영 효율은 좋지 않았다. 특히 부모 Astra가 직접 검수·조정·재지시를 오래 수행한 것이 문제였다. 이전의 “대부분 Luna”, “부모는 배정과 자동 검증만 했다”는 설명은 초기 실행의 실제 규모를 충분히 반영하지 못했다.

**범위와 집계 방법**

- 원 작업: 2026-09-08 01:39:07–17:58:48 KST, 준비·저장소 이동 포함 약 16시간 20분.
- 프록시 처리 요청부터 완료까지: 01:48:35–17:58:48, 16시간 10분.
- 이 부모 작업과 `parent_thread_id`로 연결되는 서브에이전트 76개, 총 77개 세션만 포함했다. 다른 프로젝트와 완료 후 질문·이번 감사 비용은 제외했다.
- `token_usage_record.usage`를 해당 `thread_id` 및 고유 `response_id` 기준으로 합산했다. 누적 `token_count`를 반복 합산하지 않았다.
- 77개 세션 모두 계산 결과와 마지막 `thread_token_usage`가 일치했다. 요청 11,587개, 최대 입력 256,864토큰으로 모두 공개 API의 272K 이하 구간이었다.
- 원천: 로컬 Codex rollout JSONL과 읽기 전용 SQLite 세션 인덱스. 재현 스크립트와 집계 JSON은 이 디렉터리에 보존했다.

**토큰과 비용**

표의 토큰 단위는 백만 토큰(M)이다. 일반 입력은 전체 입력에서 캐시 입력을 뺀 값이다.

| 모델·역할 | 세션 수 | 모델 응답 수 | 일반 입력 M | 캐시 입력 M | 출력 M | Standard API 환산 USD |
|---|---:|---:|---:|---:|---:|---:|
| Astra · 부모 | 1 | 2,720 | 8.374 | 359.983 | 1.089 | $498.15 |
| Terra · 서브에이전트 | 34 | 3,703 | 18.334 | 464.979 | 2.570 | $160.50 |
| Luna · 서브에이전트 | 42 | 5,164 | 13.122 | 609.957 | 2.492 | $17.81 |
| 합계 | 77 | 11,587 | 39.830 | 1,434.919 | 6.150 | **$676.46** |

총 처리 토큰은 **1,480,898,538개, 약 14.81억**이다. 이는 요청마다 다시 전달한 문맥까지 누적한 수치다. 서로 다른 콘텐츠를 14.81억 토큰 새로 읽었다는 의미가 아니다. 입력의 **97.30%**가 캐시 입력이며, 캐시가 아닌 입력은 **39,830,105개**, 출력은 **6,149,649개**다. reasoning output 1,042,802개는 출력에 포함돼 있으므로 다시 더하지 않았다.

**$676.46은 실제 청구액이 아니다.** 실행 로그에 Pro 이용 기록은 있지만 작업별 결제 영수증이나 확정 청구액은 없다. 현재 공개 Standard API 단가를 적용한 비교값이다. 실제 서비스 tier가 사용량 기록에 없어 Fast/구독 한도/추가 크레딧 청구는 확정할 수 없다. 외부 도구의 별도 비용도 포함하지 않았다.

1M 일반 입력/캐시 입력/출력당 적용 단가는 Astra $10/$1/$50, Terra $2/$0.20/$12, Luna $0.20/$0.02/$1.20이다. [OpenAI API 가격표](https://developers.openai.com/api/docs/pricing). Codex 구독 한도·크레딧과 API 청구는 구분된다. [Codex 가격·사용량 안내](https://learn.chatgpt.com/docs/pricing).

부모가 전체 환산 비용의 **73.64%**를 사용했다. 서브에이전트 전체는 $178.31이고 Luna만 보면 $17.81이다. 따라서 “저렴한 Luna에 맡겼으니 전체 작업도 저렴했다”는 설명은 성립하지 않는다. 영상당 전체 Standard 환산 비용은 약 $1.80이며, 이는 최적화 후 비용 예측이 아니다.

**병렬화는 실제로 이루어졌나**

그렇다. 작업 시작·완료 구간을 에이전트별로 합쳐 중복 구간을 제거한 뒤 계산했다.

| 실행 중 서브에이전트 수 | 시간 |
|---|---:|
| 0개 | 약 20분 |
| 1개 | 약 1시간 8분 |
| 2개 | 약 3시간 6분 |
| 3개 | 약 11시간 35분 |

평균 동시 실행은 **2.60개**, 최대는 **3개**였다. 이는 도구 대기를 포함한 작업 구간의 동시성이지 GPU 사용률은 아니다. 날짜 순차 대기는 불필요했지만, 이미 세 슬롯을 상당히 사용했으므로 전체 지연을 “병렬 실행을 안 해서”라고 설명하면 부정확하다. 날짜 병렬화 전후의 영상 난이도도 달라 속도 개선 배수를 인과적으로 계산할 수 없다.

**비효율이 확인된 지점**

1. 부모의 직접 검수가 많았다. 부모 로그에 이미지 열기 `view_image` 271회, Aside 브라우저 도구 118회가 있다. 서로 다른 영상 수는 아니며 같은 근거의 재열기도 포함될 수 있다. “부모는 배정만 했다”는 이전 설명은 초기 구간에 대해 부정확했다.
2. 부모 문맥이 과도하게 반복 전송됐다. 부모 모델 응답 2,720회에 평균 입력 약 135,425토큰이다. 이미지·도구 출력·작업 역사·긴 지시문이 누적된 상태에서 조정과 상태 확인을 반복해, 캐시를 적용해도 부모 환산액이 $498.15가 됐다.
3. 필수 형식·근거 검증 오류가 반복됐다. 도구 출력에서 `error:` 문구 1,772회가 관측됐다. 같은 오류의 재시도·재노출을 포함하므로 독립 사건 수가 아니다. 대표적으로 프레임이 claim 범위 밖 166회, clip evidence가 beat 범위 밖 110회, event steps 시간순 오류 93회가 관측됐다. 모델이 직접 작성하는 ID·시간·중첩 구조 계약이 복잡했고, 검증 후 수정 루프가 길었다.
4. 작업 완료와 에이전트 종료가 일치하지 않았다. 부모의 `followup_task` 309회, 메시지 252회가 있다. 새 묶음 배정도 포함하므로 전부 재시도는 아니다. 다만 입력 경로만 확인하고 종료, 이미 있는 packet을 없다고 보고, 전체 asset 배정을 scoped 배정으로 오해하는 실제 사례가 있었다. 부모가 재설명하거나 담당을 교체했다.
5. 아직 완전한 무인 실행기는 아니다. 자동 검증·병합·후보·웹 생성은 구현됐지만 worker 배정, 종료 여부 해석, 미완료 재시작을 부모 모델이 계속 수행했다. “자동 완료 파이프라인”과 “모델 조정 없이 끝까지 도는 작업 스케줄러”를 구분해야 한다.

환산 비용의 **90.56%**가 최종검수 중단 지시 이전에 발생했다. 이후 부모 `view_image` 및 Aside 도구 호출은 **0회**로, 부모 이미지 재검수 제거는 실제 로그에서도 확인된다. 다만 이후에도 재배정·재지시·대기 조정은 남았다.

**결과 신뢰성과 다음 실행의 우선순위**

376/376개 결과와 1,745개 후보가 기록돼 있고, 마지막 자동 실행의 완료 상태와 빈 작업 큐는 확인됐다. 관련 파이프라인 테스트 21개도 통과했다. 이는 형식·근거 연결·시간 범위 등 필수 검증 완료를 뜻하며, 모든 내용의 의미적 정확도를 독립적으로 입증한 것은 아니다. 이번 감사에서는 영상이나 추출 내용을 다시 모델 검수하지 않았다.

다음 실행의 가장 큰 개선점은 서브에이전트를 더 만드는 것보다 **부모 모델이 실행 루프에서 빠지는 것**이다.

- 작업 큐가 asset/group 소유권, 입력 경로, 출력 경로, 완료 조건을 구조화해서 전달한다.
- worker가 review와 실제 summary의 필수 검증을 통과한 완료 기록을 남겨야 작업이 완료된다. 자연어 “준비됨/진행 예정”을 완료로 취급하지 않는다.
- 단순 ID 검사·정렬·누락 필드 검사는 로컬 코드에서 처리하고, 실제 의미 판단이 필요한 오류만 모델에 돌린다. 임의로 의미나 타임코드를 고쳐 validator만 통과시키면 안 된다.
- 부모에게는 날짜별 완료 수와 해결되지 않은 오류만 전달한다. 정상 raw packet·이미지·브라우저 결과는 부모 문맥에 쌓지 않는다.
- 처음부터 같은 완료 계약으로 전체 날짜를 병렬 배정하고, 일정 시간 진행이 없는 작업만 재시작한다.
